# explain-for-understanding (2026-10-17에 `visual-first`로 흡수)

원래 설명: LLM의 결과, 복잡한 개념, 기획서와 구현 결과를 쉽게 이해하도록 설명한다. 사용자가 ASD-STE100 방식, 쉬운 설명, 이해를 돕는 도표·인터랙티브 HTML·설명 영상을 요청하거나, 조건·흐름·원인을 명확히 보여줄 필요가 있을 때 사용한다. 명료한 글쓰기 원칙을 적용하고 내용에 맞는 표현 방식을 선택한다.

# 이해를 돕는 설명

독자가 결과를 이해하고 판단할 수 있도록 설명한다. 기능과 결론뿐 아니라 조건, 근거, 한계를 보여준다. 기획서를 작성하거나 검토할 때도 적용한다.

## 설명할 내용 정하기

1. 독자가 무엇을 이해하거나 결정해야 하는지 확인한다. 요청과 대화에서 알 수 있으면 바로 진행한다.
2. 결론, 작동 원리, 필요한 조건, 예외를 구분한다. 사실과 가정, 아직 확인하지 않은 내용을 섞지 않는다.
3. 이해를 가장 잘 돕는 표현 방식을 고른다. 사용자가 지정한 형식은 따른다. 글·도표·HTML·영상을 매번 모두 만들 필요는 없다.

## ASD-STE100을 참고한 글쓰기

- 결론과 사용자가 해야 할 행동을 먼저 쓴다.
- 한 문장에서 한 가지 주요 내용을 설명한다. 문장을 줄이려고 조건이나 필요한 단어를 빼지 않는다.
- 같은 개념에는 같은 용어를 쓴다. 기술 용어는 처음 등장할 때 풀어 설명한다.
- 누가 무엇을 하는지 밝힌다. 지시와 절차는 구체적인 동사로 쓴다.
- 조건과 결과를 연결한다. 예: “구매 전에는 9쪽 중 2쪽을 읽을 수 있습니다. 4,000원에 구매하면 9쪽 전체가 내 책장에 저장됩니다.”
- 수치, 단위, 부정, 예외, 확신의 정도를 보존한다. “가능하다”를 “된다”로 바꾸거나 추정을 사실로 바꾸지 않는다.
- 문장 사이의 관계를 유지한다. 목록은 절차나 비교를 더 쉽게 읽을 수 있을 때 사용한다.
- 한국어는 자연스러운 완결 문장으로 쓴다. 한국어 문체 스킬이 있으면 함께 적용한다.

ASD-STE100은 통제 영어를 사용하는 기술 문서 규격이다. 한국어에는 명료한 글쓰기 원칙을 참고한다. 사전을 적용하지 않은 영어 문서나 한국어 문서를 “ASD-STE100 준수”로 인증하지 않는다. “80% 정도 적용” 같은 요청은 문체의 강도를 나타내는 말로 해석하며, 검증된 준수율로 보고하지 않는다.

## 표현 방식 선택

| 독자가 이해해야 할 내용 | 적합한 표현 | 제작 기준 |
| --- | --- | --- |
| 결론, 짧은 설명, 간단한 절차 | 글 | 핵심 설명만으로 충분하면 여기서 마친다. |
| 선택지, 가격, 역할, 조건의 차이 | 표 | 비교 기준과 단위를 통일한다. |
| 구조, 순서, 원인과 결과, 상태 전환 | 도표 | 작은 도표는 Mermaid를 우선 고려한다. 공유·출판용 수치 그래프는 표준 plotting 도구로 별도 파일을 만든다. |
| 사용자가 값을 바꾸며 차이를 확인해야 하는 내용 | 인터랙티브 HTML | 조작에 따라 결과가 실제로 바뀌어야 한다. 화면을 꾸미는 데 그치지 않는다. |
| 시간의 흐름, 움직임, 단계별 변화 | 설명 영상 | 사용자가 영상을 요청하거나 움직임이 이해에 도움이 될 때 만든다. |

사용자가 여러 형식을 지정하면 같은 용어와 근거를 유지한다. 각 형식이 설명하는 부분을 나눠 중복을 줄인다.

## 인터랙티브 HTML 만들기

1. 무엇을 조작하면 어떤 차이를 확인할 수 있는지 정한다. 예: 관계 방향 전환, 구매 전후 비교, 일정 선택, 조건별 결과 비교.
2. 기존 작업 공간과 사용 가능한 도구를 확인한다. 간단한 설명은 외부 서비스 없이 열 수 있는 독립 HTML로 만든다.
3. 입력에 따라 화면이 바뀌도록 구현한다. 버튼에는 행동을 드러내는 이름을 쓰고 선택 상태와 결과를 보여준다. 키보드 조작과 모바일 화면도 확인한다.
4. 예시 데이터는 예시라고 표시한다. 실제 계산, 서버 연결, 로그인, 결제가 구현된 것으로 오해하게 만들지 않는다.
5. 브라우저에서 주요 조작과 오류를 확인한다. 파일을 만든 사실과 동작을 검증한 사실을 구분해 보고한다.
6. 생성한 파일을 열거나 링크로 제공한다. 설명 자료가 원래 요청한 제품을 대체하지 않도록 한다. Kotlin 앱을 요청했다면 HTML은 검토 자료이며 실제 구현은 Kotlin으로 진행한다.

## 설명 영상 만들기

1. 영상이 설명할 핵심 변화와 짧은 장면 순서를 정한다. 움직임이 도움이 되지 않으면 글이나 도표를 제안한다.
2. 사용 가능한 영상·애니메이션 도구와 기존 자산을 활용한다. 관련 제작 스킬이 있으면 읽고 적용한다.
3. 대본, 화면의 용어, 수치와 조건을 일치시킨다. 읽을 시간과 장면 전환 시간을 확보한다.
4. 실제 영상을 렌더링하고 재생을 확인한다. 대본이나 콘티만 만들었다면 영상이 완성되었다고 보고하지 않는다.
5. 음성 서비스 가입, 유료 API 사용, 외부 공개는 요청에 포함되었거나 이미 승인된 범위에서만 진행한다. 사용할 도구가 없으면 가능한 산출물과 남은 작업을 밝힌다.

## 전달 전 확인

- 독자가 결론, 조건, 다음 행동을 이해할 수 있는가?
- 원래의 의미, 수치, 예외와 불확실성이 보존되었는가?
- 시각 자료가 이해를 돕는가? 상호작용은 설명한 대로 작동하는가?
- 예시와 실제 데이터, 구현과 검증을 구분했는가?
- 최신 정보와 출처가 필요한 주장에는 확인한 근거를 연결했는가?

## 출처와 적용 범위

- [ASD-STE100 공식 사이트](https://www.asd-ste100.org/)와 [Issue 9 PDF](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf): 명료한 기술 문서 작성 원칙의 참고 자료다. 규격 본문이나 사전을 이 스킬에 복제하지 않는다.
- [Andrej Karpathy의 2026년 10월 2일 글](https://x.com/karpathy/status/2105819303471976479): LLM 결과를 이해하기 위해 글, 도표, 인터랙티브 HTML, 설명 영상을 요청하는 접근을 참고했다. 작성 시 X 직접 열람이 차단되어 [재게시 본문](https://topicdigg.com/x/karpathy)으로 확인했다.

이 스킬은 위 접근을 사용자의 작업에 적용하도록 만든 지침이다. Karpathy가 배포한 공식 스킬이나 ASD-STE100 공식 인증 도구가 아니다. 이 스킬을 사용했다는 이유로 출처를 다시 읽었다거나 결과를 검증했다고 보고하지 않는다.
