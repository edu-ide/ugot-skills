# solve-first — 문제해결 먼저

## 왜 (이 스킬이 막는 실수)

2026-10-17 "Spring 을 Quarkus 처럼 최적화 불가능해?"에 "구조상 완전히는 안 된다"고 답하고 Quarkus·Rust 같은 기존 제품을 늘어놓았다. 사용자: "자꾸 기존에 있는 것들만 소개하고 불가능하다만 이야기함. 통념을 깨기 위해 우리가 활용한다는 가정에서 불가능하면 직접 오픈소스를 가져다 커스텀하는 원칙이 필요하다." 그런데 Spring·Hibernate·Tomcat·GraalVM 은 전부 열린 소스다. "불가능"의 실제 뜻은 "그 제품의 기본 설정으로는 안 된다"였고, 그건 답이 아니라 사다리의 첫 단이다. 같은 사용자가 이미 그렇게 일해 왔다: codex 를 포크해 codex-ilhae 로, HWP 를 자체 엔진 rhwp 로, CEF 확장 적재를 CDP 파이프로, Bazel 8 에서 깨진 rules_graalvm 을 git override 로 넘겼다(2026-10-15). 반복 실수 목록의 2(물려받은 틀)·15(단순화 후퇴·"한계" 핑계)의 한 얼굴이다.

## 규칙 — 자, 소스 위치, 사다리, 스파이크

1. **자 먼저.** 무엇을 몇으로 만들면 "된 것"인지 한 줄(예: cgroup working set ≤ 60MB, 기동 ≤ 1s, 29/29 흐름 통과). 자가 없으면 "가능/불가능"은 뜻이 없다(`multi-ruler`). 자에는 숫자와 함께 **바뀌면 안 되는 것**(기능·동작·API·데이터)을 먼저 적는다. 사용자가 따로 말하지 않았으면 기본값은 "기능 변화 없음"이고, 그 조건을 깨는 단은 사다리에서 따로 표시한다(2026-10-17: 메모리만 줄이길 원했는데 동작이 바뀌는 선택지를 대가 없이 "더 나은 선택지"로 그렸다).
2. **막는 지점을 소스 위치로.** "구조상"이라 쓰지 말고 파일·줄·함수로 쓴다(예: Spring `AbstractApplicationContext.refresh()` 가 런타임에 빈을 조립, Hibernate `SessionFactoryImpl` 생성이 기동 때 메타모델을 만듦). 열린 소스는 우리 변경 범위 안이다.
3. **사다리를 올라간다. 자를 만족하는 가장 낮은 단에서 멈춘다.**

   | 단 | 무엇 | 비용 | 남는 부담 | 기능 변화 |
   |---|---|---|---|---|
   | ① 설정 | 옵션·플래그·프로파일 | 분~시간 | 없음 | 없음, 다만 상한을 낮추면 폭주 때 대기·오류가 늘 수 있음 |
   | ② 확장점 | 공식 SPI·훅·플러그인·빌드 매크로(예: Spring `WebServerFactory`, AOT `BeanFactoryInitializationAotProcessor`, GraalVM `Feature`) | 시간~일 | 버전 추적 | 없어야 함, 대체 구현의 기본 동작 차이는 전수 확인 |
   | ③ 패치·포크 | 최소 diff 로 상류 소스를 고친다. 상류 이슈/PR 을 같이 낸다 | 일 | 패치 유지, 상류에 합쳐지면 소멸 | 없어야 함, 같은 동작을 다른 시점에 실행 |
   | ④ 부품 교체 | 막는 부품만 더 가벼운 것 또는 자체 구현으로(예: Tomcat 대신 최소 HTTP 서버) | 일~주 | 자체 유지 | 있을 수 있음, 바뀌는 동작을 목록으로 |
   | ⑤ 재작성 | 언어·프레임워크 전체 교체 | 주~월 | 전부 | 다시 만듦, 전 표면 동등 검증 필요 |

   "기존 제품 소개"는 ⑤의 후보 조사일 뿐이다. ①~④ 를 건너뛰고 ⑤ 또는 "불가능"으로 가지 않는다.
4. **하루 이하 스파이크로 잰다.** 고른 단을 가장 작은 재현물로 만들어 자로 측정한다. 추정치는 "추정"이라 쓴다(`fundamental-first` 의 프록시 측정과 같은 수).
5. **포크의 조건 셋.** (a) 최소 diff 를 패치 파일로 유지 (b) 상류 이슈 또는 PR 을 같은 날 낸다(포크가 죽을 길을 만든다) (c) 폐기 조건과 유지 담당을 적는다. 라이선스를 먼저 본다(Apache/MIT/BSD 는 됨, 그 밖은 적는다).
6. **"불가능"의 사용 조건.** 다음 중 하나를 붙일 때만 쓴다: 소스 위치(어느 줄이 막고 왜 고칠 수 없는지), 측정된 물리 한계(예: GC 가 요구하는 힙 여유 실측), 라이선스·법. 셋 다 없으면 "아직 안 해 봄, 예상 비용 N" 이라고 쓴다.

## 완전 개선 먼저 — 대가를 받아들이기 전에

대가가 보이면 받아들이기 전에 묻는다: **왜 둘 다 못 갖나?** 대가는 대개 두 가지를 같은 때, 같은 곳, 같은 조건에서 동시에 원해서 생긴다(TRIZ 의 물리적 모순). 갈라 놓으면 타협 없이 둘 다 얻는 경우가 많다. 착륙 장치가 착륙 때만 나와 있고 비행 중엔 접히는 것처럼.

| 나누기 | 묻는 것 | 예 |
|---|---|---|
| 때 | 실행 중에 하던 일을 빌드·배포·컴파일 때로 옮길 수 있나 | 실행 중 만들던 테이블 지도를 빌드 때 만들어 이미지에 담기, 네이티브 이미지 |
| 곳 | 같은 프로세스·노드가 아니라 다른 곳에서 할 수 있나 | DB 를 노드 밖 관리형 DB 로 옮겨 노드 메모리에서 빼기 |
| 조건 | 늘 하지 말고 필요할 때만 할 수 있나 | 드물게 쓰는 기능만 처음 쓸 때 준비 |
| 부분과 전체 | 부분마다 따로 내던 비용을 전체에서 한 번만 낼 수 있나, 또는 그 반대 | 여러 프로세스가 같은 고정 비용을 따로 내는 것을 하나로 |

절차:
1. 선택지마다 **얻는 것 / 잃는 것 / 잃는 것을 없앨 나누기** 세 칸을 쓴다. 잃는 것에는 기능·동작 변화, 지연·처리량, 운영 위험, 유지 부담을 모두 넣는다.
2. 잃는 것이 0 인 후보(완전 개선)가 있으면 그것부터 스파이크로 잰다.
3. 없으면 남는 대가와 그 이유(네 나누기가 왜 안 되는지)를 적고, 사용자 조건을 깨는지 표시한다.
4. "어쩔 수 없는 대가"라고 쓰려면 네 나누기를 시도한 기록이 있어야 한다. 기록이 없으면 "아직 안 갈라 봄"이라고 쓴다.

## 관문(통과 조건)

- 가능 여부 질문의 답에 사다리 표(단·비용·기대치)와 첫 스파이크(무엇을 하루 안에 재는지)가 있다.
- 대가가 남은 선택지마다 네 나누기(때·곳·조건·부분과 전체)를 시도한 줄이 있다.
- 선택지마다 **기능 변화와 대가**가 같은 줄에 있다. 대가가 빠진 선택지를 "더 나은 선택지"로 그리지 않는다. 사용자 조건(예: 기능 변화 없음)을 깨는 선택지는 조건 밖으로 따로 묶는다.
- "불가능/구조상/한계"라는 말마다 6번의 근거가 붙어 있다.
- 기존 제품 이름은 '참고:' 줄(`reference-first`)이나 ⑤ 후보로만 등장한다.

## 금지

- "X 는 구조상 안 됩니다"로 문단을 끝내기.
- 가능 여부 질문에 제품 비교표만 내기.
- 자 없이 "거의 비슷하게는 됩니다/안 됩니다" 말하기.
- 포크를 상류 이슈 없이, 폐기 조건 없이 들이기. (`ssot-extend-not-fork` 는 우리 코드의 정본 이야기이고, 이 스킬은 남의 소스를 우리 범위에 넣는 이야기다. 둘은 "포크를 영원히 두지 말라"에서 만난다.)

## 형제 원칙

- `fundamental-first`: 무엇을 고칠지(우회 대신 근본). 이 스킬은 어디까지 고칠 수 있는지(남의 소스도 우리 범위).
- `reference-first`: 기존 제품·1차 소스를 본다. 이 스킬은 그것을 답이 아니라 사다리의 재료로 쓴다(기준 제품의 소스가 포크의 설계도다. 예: Quarkus 의 Hibernate 빌드타임 부팅이 Spring 확장·포크의 참고).
- `multi-ruler`: 자 먼저.
- `recall-before-reinvent`: 같은 포크를 이미 했는지 먼저 본다.
