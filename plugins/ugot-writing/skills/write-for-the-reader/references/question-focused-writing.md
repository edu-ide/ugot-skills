# question-focused-writing (2026-10-17에 `write-for-the-reader`로 흡수)

원래 설명: 자기소개서·지원동기·면접 답변·제안서를 질문에 맞고 자연스럽게 작성하거나 수정한다. 경험에 억지 의미를 붙이거나 회사 가치와 기계적으로 연결한 글, 질문과 어긋나는 내용, 불필요한 주장과 사족을 고쳐 달라는 요청에 적용한다.

# 질문에 맞는 지원서 작성

질문에서 필요한 답을 사용자의 사실과 말투로 쓴다. 자연스러움은 단순히 짧게 쓰는 것이 아니다. 독자가 앞 문장 다음에 왜 이 문장이 오는지 이해할 수 있게 연결한다. 좋은 지원자처럼 보이게 하려고 사용자가 말하지 않은 성격, 동기, 교훈, 목표를 만들어 내지 않는다.

## 억지로 만들지 않는 서술

- 문항의 답을 한 문장으로 먼저 정리하고, 그 답에 필요한 경험을 고른다. 기존 글이 질문과 어긋나면 문구만 다듬지 말고 필요한 사실에서 다시 쓴다.
- 문단마다 중심 이야기를 두고, 그 이야기가 이해되는 만큼 설명한다. 경험마다 교훈·역량·회사 가치·입사 후 포부를 붙이는 틀을 강제하지 않는다. 단락 수와 글자 수를 채우기 위해 내용을 늘리지 않는다.
- 간결하게 쓰라는 요청을 분량을 크게 줄이라는 뜻으로 해석하지 않는다. 질문과 관련된 경험의 배경, 맡은 역할, 구체적인 방식과 결과는 충분히 설명한다. 불필요한 문장을 정리한 뒤 내용이 빈약해졌다면 확인된 사례와 맥락으로 보완한다.
- 성향에는 평소 어떻게 배우거나 행동하는지, 경력에는 실제 맡은 일과 역할, 비전에는 앞으로 하고 싶은 일을 쓴다. 'AI와 일하는 태도'를 AI 제품 기능 목록으로, '몰입한 경험'을 기술 소개로 바꾸지 않는다.
- 지원 이유와 기여는 회사의 실제 업무에 관심을 가진 이유와 맡을 수 있는 일을 설명한다. 공고의 모든 업무를 경력 하나씩에 대응시키거나 모든 항목 끝을 지원동기로 마무리하지 않는다.
- 사용자가 여러 요소를 종합해 판단한다고 하면 그 관점을 보존한다. 근무조건·비전·분위기의 사전식 정의를 나열하거나, 확인하지 않은 회사 조건을 좋다고 평가하지 않는다.
- 기술 세부는 답의 의미를 분명하게 하는 사례만 남긴다. 이미 경력·프로젝트 표에서 설명한 구현 내용을 다른 문항에 다시 늘어놓지 않는다. 문항에 필요한 구체성까지 없애지는 않는다.
- 스스로에게 의미가 있었던 경험은 설명할 수 있지만 '이 경험을 통해 중요한 것을 깨달았습니다' 같은 결론을 자동으로 붙이지 않는다. 확인된 결과나 경험을 말한 곳에서 자연스럽게 끝낼 수 있다.
- 낭독했을 때 실제 사람이 할 법한 말인지 확인한다. '역량을 발휘하며 지속적으로 기여', '전문성을 존중해 완성도를 높임' 같은 표현은 의미가 있는 맥락에서만 쓴다. 쉬운 표현으로 바꿔도 뜻이 유지되면 쉬운 표현을 택한다.

## 질문과 제목을 기준으로 판단하기

- 문항에서 실제로 요구하는 답을 먼저 파악한다. 제목과 문항이 다르면 문항을 우선한다.
- 문장의 역할은 직접 답변, 그 답의 근거, 정확한 이해에 꼭 필요한 설명 중 하나여야 한다. 어느 역할도 없으면 줄이거나 뺀다.
- 경력 문항에는 경험과 역할, 성향 문항에는 행동 방식, 지원동기 문항에는 지원 이유와 관련 기여를 중심으로 쓴다. 같은 경험도 문항에 맞는 부분만 사용한다.
- 회사 선택 기준은 무엇을 중요하게 보는지와 해당 회사가 그 기준에 맞는 근거를 연결한다. 자신의 경험 설명이 회사 선택 기준을 가리지 않게 한다.
- '비전', '가치관', '흥미' 같은 말이 모호하면 사용자가 뜻한 내용을 풀어 쓴다. 구체화한다는 이유로 사용자의 기준을 새로운 신념이나 기술 목표로 바꾸지 않는다.
- '첫째·둘째' 등의 구분이나 기준의 개수 자체를 문제 삼지 않는다. 필요한 만큼 사용하며 각 기준과 근거가 대응하는지 확인한다. 특정 문단 수나 서술 틀을 강제하지 않는다.

## 불필요한 반박 여지 줄이기

- 질문의 답을 더 분명하게 만들지 않는 부정적 평가, 실패 원인 추측, 도구나 동료에 대한 책임 전가를 덧붙이지 않는다. 원인이나 실패가 문항의 핵심이면 근거에 따라 정확히 설명한다.
- 사실로 확인하지 않은 성과 수치, 생산성 향상, 테스트 수행, 운영 결과, 회사 내부 문화는 주장하지 않는다. 필요한 사실을 확인할 수 없으면 해당 주장만 좁히거나 확인 필요 상태를 짧게 밝힌다.
- 본인의 역할을 팀이나 다른 사람의 역할까지 넓히지 않는다. '혼자 전부', '모든 과정', '완벽하게', '반드시' 등은 범위와 근거가 있는 경우에만 쓴다.
- 회사 선택 기준을 회사에 제시하는 근무 조건이나 혜택 요구처럼 바꾸지 않는다. 배움과 성장도 사용자의 실제 기준이면 그대로 다룬다. 실제 조건이나 보상에 관한 요청도 보존한다.
- 불필요한 방어 문장을 본문에 넣지 않는다. 검증되지 않은 성과 주장을 빼면서 '과장하는 것은 아니지만', '아직 검증하지는 않았지만' 등의 변명으로 대체하지 않는다.
- 기술 이름은 문항의 답을 이해하는 데 도움이 될 때 사용한다. 이름을 나열하기보다 어떤 일을 했고 무엇을 확인했는지 설명한다. 전문성을 보여주는 데 필요한 구체성은 남긴다.
- '독자가 근거를 물을 수 있다'는 이유만으로 필요한 경험이나 구체적인 사실을 삭제하지 않는다. 근거 있는 설명과 불필요한 주장 확대를 구분한다.

## 사실·판단·계획 구분하기

- 사실은 사용자 자료나 확인한 출처에 근거해 쓴다. 역할, 시점, 수행 범위와 확인된 결과를 보존한다.
- AI를 활용해 개발한다는 사실만으로 코드를 직접 이해하거나 검토하고, 원리를 공부하거나 테스트한다는 습관을 만들어 넣지 않는다. 기능을 정하고 AI에 구현을 맡기는 일, 결과를 사용하고 개선하는 일, 소스 코드를 읽고 이해하는 일은 각각 확인된 범위에서만 쓴다.
- 사용자가 실제 행동과 다르다고 정정한 표현은 해당 문장뿐 아니라 같은 가정을 담은 다른 문장과 대응표에서도 고친다. 좋은 개발자로 보이게 하려고 사용자의 AI 활용 방식을 수동 코드 학습 방식으로 바꾸지 않는다.
- 사용자가 개발 방식이나 경험을 직접 확인해 주면 그 정정을 최신 사실로 적용한다. 예를 들어 '테스트 주도 개발을 한다'는 확인은 현재 개발 방식으로 쓸 수 있다. 이를 특정 테스트 수행 이력, 수치나 성과까지 확인한 것으로 넓히지는 않는다.
- 공고에 나온 업무와 지원자의 해석을 구분한다. 공고의 코드 리뷰 업무를 근거로 협업 방식이 자신의 기준에 맞는다고 판단할 수 있지만, 실제로 경험하지 않은 회사 문화를 확정하지 않는다.
- 앞으로의 기여를 과거의 실적으로 바꾸지 않는다. 계획은 의지와 맡을 행동으로 표현하고 결과를 보장하지 않는다.
- 불리한 사실, 필수 고지, 정확성에 필요한 한계를 숨기거나 바꾸지 않는다. 이 스킬은 기만이나 책임 회피를 위한 지침이 아니다.

## 소재가 부족하면 사용자에게 묻기

- 질문에 답하려면 필요한데 자료에 없는 개인 경험, 동기, 감정, 판단 이유, 협업 과정은 먼저 사용자에게 묻는다. 그럴듯한 사례나 행동 습관을 추측해서 작성하지 않는다.
- 필요한 소재와 쓰려는 위치를 짧게 설명하고, 사용자가 쉽게 답할 수 있는 질문을 1~3개로 좁힌다. 프로젝트·맡은 일·당시 행동·확인한 결과 중 필요한 것만 묻고, 기술 세부를 불필요하게 요구하지 않는다.
- 구체적인 프로젝트 사례를 모든 문항의 필수 조건으로 삼지 않는다. 태도·기준·개발 방식에 관한 문항은 사용자가 그 방식을 택한 계기, 판단 이유와 원리만으로도 충분히 답할 수 있다. 사용자의 생각을 듣는 대신 구현 사례나 성과를 강요하지 않는다.
- 기존 자료에 답이 있으면 다시 묻지 않는다. 확인된 소재만으로 필요한 설명이 충분하면 그대로 작성한다. 구체적 사례가 글을 더 좋게 만들 수 있는 경우에는 선택적으로 질문한다.
- 답변을 기다리는 동안 이미 확인된 문항은 계속 작성한다. 필수 사실을 기다리는 문장은 완성본에 지어 넣지 않는다. 선택적인 추가 소재가 오지 않으면 확인된 내용으로 마무리하고, 없는 사례를 채우지 않는다.
- 사용자가 답하면 말한 범위와 의미를 보존해 글에 반영한다. 제안한 예시를 사용자의 실제 경험으로 바꾸거나, 짧은 답에서 성과 수치·갈등·교훈을 만들어 내지 않는다.

## 마지막 문장 검토

각 문장을 읽고 다음을 판단한다. 검토표를 사용자가 요청하지 않았다면 검토 과정을 길게 출력하지 않는다.

1. 이 문장을 빼면 문항의 답이나 필요한 근거가 빠지는가?
2. 이 문장이 실제 자료보다 더 넓은 성과·역할·확신을 주장하는가?
3. 문항과 무관한 비판·변명·조건·새 주제를 추가하는가?
4. 독자가 한 번 읽고 질문의 답을 이해할 수 있으며, 앞뒤 문장이 자연스럽게 이어지는가?
5. 실제 경험을 설명하는 대신 좋은 사람처럼 보이기 위한 의미·교훈·포부를 덧붙였는가?

불필요한 문장은 삭제하고, 필요한데 모호한 문장은 근거가 확인되는 범위로 다시 쓴다. 장점을 만들기 위해 경험이나 감정, 갈등 해결 과정을 꾸며내지 않는다. 여러 항목을 함께 고칠 때는 제목만 읽어도 각각 무엇에 답하는지 드러나고, 본문을 읽어도 그 주제가 유지되는지 확인한다.

## 결과 전달

- 고쳐 달라는 요청에는 설명보다 완성된 문안을 먼저 제공한다. 수정 이유는 이해에 필요한 부분만 짧게 설명한다.
- 평가를 요청하면 실제 문장과 근거에 관한 문제만 지적한다. 막연한 가상 심사자를 만들어 불필요한 불안을 더하지 않는다.
- '아무도 트집 잡을 수 없다'고 보장하지 않는다. 무엇을 정리했는지 구체적으로 말한다.
- 문안 밖의 안내도 요청과 관련된 것만 제공한다. 글자 수, 파일 반영 여부, 실제 검증 결과가 필요한 경우 본문과 구분해 짧게 안내한다. 복사할 지원서 문안에 작업 로그, 내부 검토 메모, 출처 표식을 섞지 않는다.
- 이 스킬은 외부 업로드·제출·공유 권한을 추가하지 않는다. 원본 파일 반영은 기존 요청 범위와 연결된 편집 도구의 지침을 따른다.
- 취업 지원의 외부 업로드·제출·지원 메일 발송 또는 수정본 교체 요청으로 이어질 때는 [지원서 최종 제출 승인](../application-final-approval/SKILL.md)을 함께 적용한다. 실제 최종본과 제출 대상을 먼저 보여주고 명시적인 제출 승인을 받은 뒤 실행한다. 회사·직무 선택이나 작성·검수 요청만으로 제출하지 않는다.
